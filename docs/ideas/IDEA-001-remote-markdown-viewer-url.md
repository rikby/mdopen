# Remote Markdown viewer via encoded URL

## Idea

Given a URL to a `.md` file, paste it into the mdopen GitHub Pages site and get
back a new URL that embeds the target URL; opening that URL renders the remote
Markdown with the existing mdopen styling.

## Investigation

### Feasibility: yes, with one correction

The word "hash" cannot be literal. A cryptographic hash is one-way, so an
endpoint cannot "unpack" it without a hash-to-URL database, and GitHub Pages is
static-only — no backend, no database. The embed must be a **reversible
encoding**: `base64url` of the target URL, carried in the URL fragment.

### Verified facts (2026-08-26)

- `raw.githubusercontent.com` responds with `access-control-allow-origin: *`,
  so a Pages page can `fetch()` GitHub-hosted Markdown cross-origin.
  `gist.githubusercontent.com` behaves the same.
- `github.com/.../blob/...` pages send no CORS headers — direct fetch fails.
  The page must rewrite blob URLs to raw URLs (pure client-side string
  rewrite) before fetching.
- base64url round-trips cleanly; ~33% length growth. Typical GitHub raw URL
  (61 chars) → 82 chars encoded → ~130-char shareable URL. No length problem.
- `templates/editor-script.html` + `edit.html` already prove the hard part:
  CDN-loaded markdown-it + plugins + highlight.js rendering into
  `.markdown-body` with the same pipeline as the CLI renderer
  (frontmatter, callouts, mermaid). A viewer reuses that machinery.

### Proposed shape

1. `view.html` (GitHub Pages only, generated by `scripts/build-pages.js` like
   `edit.html`).
2. Without a hash: shows a small "paste Markdown URL" form; on submit,
   normalizes blob → raw, base64url-encodes, and navigates to
   `view.html#u=<encoded>`.
3. With `#u=<encoded>`: decodes, `fetch()`es the Markdown, renders via the
   shared client-side pipeline. Fragment is used so nothing is sent to any
   server; the page never proxies content.

### CORS survey (2026-08-26)

Same-Origin Policy: `fetch()` from the Pages page can only read a cross-origin
response when the target server answers with `Access-Control-Allow-Origin`.
The network request may succeed; the browser still hides the body from JS.

| Host | Result |
|------|--------|
| `raw.githubusercontent.com` | `access-control-allow-origin: *` — works |
| `gist.githubusercontent.com` | `access-control-allow-origin: *` — works |
| `cdn.jsdelivr.net/gh/...` | `access-control-allow-origin: *` — works (good blob→raw fallback) |
| `unpkg.com` | `access-control-allow-origin: *` — works |
| `gitlab.com/.../-/raw/...` | HTTP 200 but **no** ACAO — fetch fails in browser |
| `example.com/file.md` | no ACAO — fails |

Mixed content: the Pages site is https, so plain-`http://` targets are blocked
by the browser regardless of CORS; force https.

### User direction (2026-08-26)

No mdopen-side allowlist. Any URL is accepted; the target server's own CORS
header is the gate. Design: direct fetch first (covers GitHub, gists, jsDelivr,
unpkg, most CDNs); on CORS failure show a clear error plus an **opt-in**
"retry via public CORS proxy" action rather than silent proxying.

### Risks / open decisions

- **CORS boundary**: hosts without `access-control-allow-origin` cannot be
  read directly by any static page (see survey above). Opt-in public CORS
  proxy covers them at the cost of the proxy seeing/tampering with content —
  and the viewer renders with `html: true`, so tampered content means injected
  markup under the Pages origin. This makes the sanitization question below
  more important, not less.
- **Untrusted input**: remote Markdown renders with `html: true`, same as the
  editor today. Rendering arbitrary remote documents under the Pages origin
  raises the XSS stakes. Mermaid is already `securityLevel: 'strict'`. Decide
  whether to sanitize HTML (new dependency) or restrict/disallow raw HTML on
  the viewer path.
- **Scope guard**: editor precedent applies — viewer must stay out of the
  binary build (`AGENTS.md` rule).

### Effort

S — one new Pages-generated page, one browser script that mostly reuses
`editor-script.html` machinery, plus a paste-URL form. No new runtime deps
required.

## Decision

Promoted 2026-08-26 — verified feasible as a pure client-side GitHub Pages
page (base64url in the fragment, direct fetch, opt-in proxy fallback,
no allowlist). Committed as MDOP-002 (Feature, Medium).
